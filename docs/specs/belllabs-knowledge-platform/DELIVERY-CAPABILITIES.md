# Delivery, capability registration and release qualification

Status: implementation specification for the BellLabs Knowledge Platform planning packet. This document defines required future behavior; source observations below do not certify a deployment. Linear publication and issue identifiers are supplied by the packet owner. No runtime, database, seed, provider, deployment or fixture operation is authorized by this document alone.

## Problem and outcome

An agent can currently find a procedure in a repository without having its tools installed, its bytes available to a worker, or authority to call it. The existing Mission Control catalog and Knowledge Services operation catalogs are useful foundations, but neither the directory move nor an existing seed establishes complete domain capability coverage. The platform must make every domain skill, MCP server, MCP tool and CLI entrypoint visible in its application's PostgreSQL capability catalog, with an exact version, accountable owner, executable contract and explicit readiness disposition.

Deliver one reusable Knowledge Services core and independently operated application/domain services. The AI Engineer and Biotech applications consume the same compatible platform releases while retaining separate installation identities, catalogs, grants, storage, knowledge authority and runtime credentials. Mission Control remains the general scheduler and capability consumer. Knowledge Services owns its algorithms, durable knowledge operations and admission policy; a domain service owns its domain writes. The AI Engineer database contract and Biotech graph/schema contracts retain their existing owners.

## Complete inventory and catalog contract

Create a versioned, machine-readable inventory in each owning repository and a deterministic application assembly manifest. These are proposed delivery artifacts, not existing schemas. The assembler must read declared public roots; it must not crawl private notes, caches, dependencies, retained worktrees, runtime receipts or compatibility junctions. Machine-global connector installation is discovery input only, never authority to publish an asset.

The AI Engineer assembly includes the shared KS distributions bound to AI Engineer plus every skill, MCP contract and CLI entrypoint owned by active AI Engineer repositories and its domain workspace skill roots. The Biotech assembly includes the Biotech knowledge service, knowledge catalog and other active Biotech repositories plus domain workspace skill roots, including vendored Neo4j and provider skills. Common Mission Control/runtime skills are installed independently in both application catalogs when applicable. Shared KS skills intended for both applications receive separate application manifests and admissions. Repository onboarding and removal must update the declared root registry so a forgotten repository cannot silently disappear from coverage.

Every discovered asset must have exactly one accountable catalog disposition. Development, schema-maintenance, deployment and administrative skills are included; they receive restricted grants and host support rather than disappearing from inventory. Duplicate copies resolve to one canonical owner plus source aliases. Unsupported, unavailable, rejected or retired items stay visible with reasons; discovery is never silently promoted. Required runtime capabilities that cannot be qualified block release.

Each inventory entry records:

- Stable namespaced capability ID, source owner/repository, source revision and path within the released bundle; upstream origin, license and modification policy when vendored.
- Asset kind and contract version; immutable release/package/image identity and artifact digest; content manifest digest; upstream version and dependency lock where applicable.
- Public operation identity and transport/profile bindings, exact CLI argument grammar or MCP tool name and input/output schemas, effect class, idempotency/retry/cancellation behavior and required custody or receipt contracts.
- Applicability to each application, supported/unqualified/unsupported lane profiles, required secret-reference names, credential audience, network/provider prerequisites, dependency pins and compatibility requirements.
- Catalog disposition, admission evidence, expected grants, replacement/retirement metadata and provenance. Operational health/readiness is separate from immutable artifact definition.

The inventory must include each CLI binary and every callable public subcommand/entrypoint as well as one row per MCP server and one row per tool. A skill naming a CLI or MCP tool contributes a dependency edge, not proof of implementation. Every published operation must either map to an entry or have an explicit contract reason for being non-callable. The completeness check compares sets, not a frozen count: source assets = canonical registered assets plus explicit duplicate/retired source dispositions; published callable surfaces = registered invocation bindings. Any unaccounted source, command or tool fails the release check.

Map skills to `skill_bundle`, servers to `mcp_server`, tools to `mcp_tool`, and CLI entrypoints to `operation_binding`. No new `cli` kind is assumed. The CLI invocation contract must specify a trusted installed executable/package identity, argv template, typed input/output, allowed working-directory and filesystem/network profile, timeout, environment reference names, effect classification and authoritative receipt behavior. It must use structured argv, not arbitrary shell expansion. If existing operation-binding validation cannot represent that contract, extend its versioned definition and the common database contract additively; do not smuggle executable authority through unvalidated manifest JSON.

Proposed per-app seed bundle names may follow `mc.app.<application>.knowledge-platform@<version>`. Naming is finalized in implementation against the existing seed loader; it does not introduce a second migration owner. The same definitions may be generated for both applications, but each receives its own installation IDs, storage prefixes, decisions, grants and receipts.

## Registration, custody and admission flow

1. **Assemble and inspect.** Build from a pinned revision and frozen dependency lock. Enumerate source skill packages, package `bin` declarations, command tables, registered MCP handlers and HTTP client contracts. Produce a diff against the previously installed application assembly. Validate ownership, licenses, strict schemas, transport/profile exclusions and dependency closure without calling a provider or domain mutation.
2. **Capture contracts.** Start exact released MCP artifacts in a restricted disposable conformance environment and record initialization, protocol version and `tools/list` schemas with capture provenance. Capture must have no production credentials. Test each CLI from its installed package in an empty consumer directory. Remote server definitions pin a tool-contract snapshot and compatible endpoint/service release, since a remote URL alone cannot pin server bytes. Unexpected tools/schema drift quarantine the affected binding; never automatically grant additions.
3. **Publish bytes.** Put complete skill directories, references, scripts and required assets into the application's private `capability-bundles` bucket under `<application>/<kind>/<capability_id>/<version>/<manifest_sha256>/<path>`. Preserve exact released bytes and per-file digest/size; choose any line-ending canonicalization before release and never normalize downloaded bytes. Reject traversal, external symlinks and package-external references. Text-only backends must reject unsupported binary assets explicitly rather than omit them.
4. **Register proposed versions.** Record the immutable manifest and compatibility requirements in that application's catalog, with source and custody provenance. Upload and SQL registration are independently resumable; reusing an object requires byte verification. A failed registration may leave an orphaned immutable object for later reviewed garbage collection, never an overwritten object.
5. **Admit and grant.** An authorized catalog operator records `asset_decision` evidence after custody, contract and host qualification. Tenant actors receive explicit `capability_grant` rows for exact versions and bounded effects. Administrative/deployment operations require separate principals; read-only stages never inherit publish, write, restore or deployment authority. Skill text, plugins, search results and service health cannot create grants.
6. **Bind and materialize.** Mission compilation resolves `<capability_id>@<version>#sha256:<manifest_digest>`, checks admission and dependency closure, and writes the immutable execution binding. The application resolver supplies application-bound credentials server-side. Workers download via short-lived signed URLs and verify every file before projection. Enforce the qualified filesystem isolation method and test attempted mutation; pathname validation alone cannot establish a read-only mount.
7. **Invoke and reconcile.** Worker launch verifies that the exact admitted capabilities are installed, compatible and reachable. MCP and CLI adapters pass authenticated application/tenant context and return durable handles and attributable receipts. Domain writes remain domain service decisions. A lost response is reconciled against authoritative receipts before retrying a mutation. Grant revocation and disabled applications take effect at invocation despite a previously pinned revision.
8. **Reconcile installation.** Compare expected assembly, actual app catalog rows, custody objects, worker-available bindings and search projection. Report missing, extra, drifted, proposed, admitted, revoked and retired entries distinctly. Installation success requires application-specific receipts; a successful install in one database does not stand in for the other.

Search is a rebuildable discovery projection. Filter by application, tenant grants, kind, effects and qualified lane before ranking. Rebuilding search must not recreate a grant or repair a revoked capability. No catalog bundle carries credential values, arbitrary database DSNs or authority to choose another application.

## Versioning, aliases and retirement

Keep published manifests, installed seed versions and applied migration bytes immutable. A changed skill, tool schema, binary, dependency lock, host-support claim or credential requirement produces a new version and digest. Exact pins never mean `latest`, a floating package range or the current checkout. Revocations block new execution immediately; historical bindings and receipts remain attributable.

Aliases are authoring/discovery conveniences resolved to exact canonical pins before commit. They cannot rewrite an already committed revision. Introduce a versioned alias/replacement contract through the catalog owner if the current definition lacks one; this is proposed work, not an assumed existing alias table. Ambiguous names produce a validation blocker. Legacy CLI/MCP spellings are not restored merely to satisfy stale fixture code. Track old names as retirement metadata and provide explicit migration diagnostics; executable aliases require a reviewed compatibility contract and bounded removal gate.

Consolidating the eleven-plus-one KS skill inventory into eight canonical skills is expand, migrate, contract: publish new bundles with complete operation/reference coverage; migrate all consumers and exact dependency pins; then retire prior versions after demonstrating no active configured consumer requires them. An old Mission Control coordinator skill must similarly be retired together with its consumer change, not edited in its frozen seed. Do not re-admit a retired research service under a renamed path.

Retirement records a replacement or no-replacement disposition, reason, affected consumers, last supported release and archival retention. Retired assets remain inspectable but cannot be newly bound. Running work either drains under explicit policy or is canceled through the owning control contract. Physical deletion is a separate retention action.

## Providers and consumer conformance

External acquisition and research providers, model routes, embedding services, parser/Docling services, object storage, Neo4j, application PostgreSQL, Temporal and Agent Server are dependencies with distinct owners. A dependency manifest states whether each requirement is needed for startup, a specific operation or an optional feature. Required dependencies fail closed; optional features report a typed unavailable state without disabling unrelated operations. Secret availability is checked by name and scope without logging values. Missing identity, license, rate-limit, endpoint, package checksum or tool-schema evidence remains a visible blocker.

Retain reviewed existing provider pins as provenance until a new reviewed release changes them; this task makes no claim those versions are latest. Existing limitations include a missing recorded BioMCP wheel digest, unverified EdgarTools extra resolution, third-party skill metadata issues, and cloud PubMed transport qualification. Resolve these against the chosen artifact rather than treating a transcribed seed as live evidence. Do not modify verbatim vendored bytes silently to appease a loader; publish a separately owned adapter or a reviewed patched distribution with new provenance where necessary.

Consumer conformance runs through public installed HTTP/client, MCP and CLI boundaries. KS API/MCP/workers continue calling application services in process; another repository uses published contracts rather than internal algorithm imports. Validate actual metadata loaders and host projections for every claimed lane: required skills loaded exactly once, zero silent skips, links contained within the bundle, expected tools present, forbidden tools absent, correct secret-reference projection and exact digest preservation. Schema validation alone is insufficient.

Maintain separate results for static contract validation, installed-package conformance, isolated database/worker integration, live provider reachability and final workflow fixtures. A deterministic fake can prove protocol/error handling; it cannot establish provider availability, model quality or domain correctness. Conformance environments do not inherit personal/global MCP configuration. The maintained consumer fixture owner must be selected within the current platform/app test ownership; the retired research agent cannot be its owner.

## Shared core and domain service release contract

Core packages have no dependency on domain repositories, arbitrary sibling paths or a universal knowledge schema. Existing `@aiengineer/*` package names and database bindings are preserved until a separately versioned extraction changes them. Each extraction uses an additive public seam first, then consumer migration, then removal. Domain services adopt shared capabilities through published service/client/CLI/MCP contracts; cross-repository imports of private algorithm packages remain prohibited. Shared source never grants shared data authority.

Every deployment release records a compatibility matrix with exact core packages, public KS contracts/client/CLI/MCP versions, domain adapter/service version, domain schema contract digest, Mission Control component/seed releases, supported runtime and parser versions, worker/task-queue versions, capability assembly digest and configuration profile digest. The matrix is a proposed artifact that must become machine-validated release input. A worker rejects an incompatible operation/schema version rather than guessing or loading another domain's credentials.

| Owner | Release responsibility |
| --- | --- |
| Shared KS repository | Core/application contracts, algorithms, transports, durable knowledge workers, shared skills, parser boundaries and published release evidence. |
| AI Engineer database contract | AI Engineer-owned migrations, generated types and compatibility release; KS consumes the pinned package. |
| Biotech schema/graph owners | Domain SDL/graph contracts, sidecars, graph migrations and domain service compatibility. Re-pin generated workspace inputs through their owner. |
| Mission Control database-contract package | Common Mission Control SQL and installer releases, additive catalog changes and immutable seeds; install independently into each app PostgreSQL database. |
| Application/domain services | App adapters, caller policy, provider configuration, domain writes, independent deployment locks and rollback decisions. |
| Consumer/application operators | App-bound grants/credentials, installed assembly, worker readiness, runtime topology and final acceptance evidence. |

Release compatibility uses expand, migrate, contract. Add backward-compatible wire/schema forms before upgrading consumers; keep old forms supported until all declared callers and in-flight work have migrated. Domain schema changes originate with their owner. Register new capability versions alongside old admitted versions, migrate callers explicitly, then retire the old versions. A single shared release can have different deployment dates and readiness states in each app.

Drain or version-route durable work during upgrades. Record the originating operation contract, implementation/profile version and domain schema digest in durable operation context. Use worker versioning or versioned queues and compatible handlers for old work; do not replay old operations against incompatible new code. Test lease fencing, cancellation, crash recovery, lost callbacks and duplicate delivery at public worker/receipt seams. Mission Control's Temporal workflows and KS durable operation workers retain their separate lifecycle authority.

Before each app rollout, inspect actual target identity, installed receipts, extension prerequisites, restricted roles and schema fingerprint. Apply only the owner's planned additive releases, then runtime storage/bucket policy prerequisites, then compatible services/workers and capability seeds, then grants and admission. Keep app admission disabled until its required gates pass. Use rollback to prior application/worker releases only when schema compatibility allows it; otherwise stop admission and forward-fix. Never promise that a destructive down migration is the rollback plan.

Extend the existing Git-driven workflow with changed-contract routing, cross-owner consumer impact and capability assembly checks. A shared-core change must name all affected application release matrices and consumer checks; a domain-only change must retain its own contract tests. Capture evidence against exact source and policy fingerprints, supersede stale proposals, and retain independent deterministic check results even when the reviewer reports no findings. Changes to migrations, workflow policy, protected evidence, grants and credentials require the normal owning review path.

Existing local policy selects Cursor `grok-4.7-high`, with bounded attempts, isolated homes/worktrees and no inherited personal MCP configuration. ## Hard gates and evidence semantics

1. **Planning published:** final spec, decisions and all implementation/qualification tickets exist in the official Linear project with provenance, ownership, acceptance criteria and native dependencies. This proves planning only.
2. **Implementation complete:** every feature, shared-core/domain adapter, product consumer, schema compatibility, skill consolidation, capability registration, worker and maintenance slice required by the packet is integrated. Required lower-level unit, contract, installed-package and isolated integration checks have run; no known failed assertion is relabeled green. Final fixtures cannot start while any such implementation ticket is open, blocked or merely proposed.
3. **Release qualified:** each application's exact release manifest, complete assembly and required host/provider/storage/runtime prerequisites pass independently. Deployment configuration and service readiness have attributable operator evidence. Required assets have custody, admission, grants and worker availability; proposed assets cannot satisfy a required capability. Existing historical replay receipt failure remains an explicit failed gate until the original evidence is recovered with provenance or a separately approved owning contract decision changes the requirement; never manufacture/reseal a substitute.
4. **Final fixture ready:** only after gates 2 and 3, pin disposable/non-production targets, released consumer binaries, fixture inputs and gold, schema/provider/model versions, ceilings, permitted effects and restoration procedures. Freeze acceptance criteria before observing results. Ensure every implementation dependency is a hard native blocker, not just prose on this ticket.
5. **Final fixture accepted:** run complete workflows through public contracts with fresh consumer sessions, exact capability pins, real sync/async paths where claimed, deterministic receipts and independently evaluated outputs. Include app/tenant isolation, evidence/citation replay, duplicate delivery/lost-response recovery, controlled domain writes/publication, cancellation and authorized restoration. Distinguish technical completion, valid outputs, mission acceptance, domain admission and publication. An experiment or smoke test cannot substitute for this gate.

No end-to-end fixture runs now or during unfinished implementation. Lower-level tests needed to implement contracts and worker behavior may run in their slices; they must not be presented as full workflow fixture acceptance. Fixture preparation can be specified now, but execution and final acceptance are last. Report each result as passed, failed, blocked or unrun with revision, scope, environment and limitations. A known failure is neither a pass-with-exception nor evidence of an unrelated deployment failure.
